## 3. 基准是新扫描，而不是抄录历史结果

实际运行默认正式 `scan_candidates` 检查全部 50 项，同时运行未改动的原生发现检查器，
获得独立的重叠阻碍记录。每项保存完整 worker 命令、返回码、耗时、stderr、正式结果和发现层结果。
单任务进程有 300 秒硬时限，控制器最多两个独立种子进程；失败数量保持 null，不转成零候选。
本次基准 wall time 为 168.343 秒，扩展扫描为 260.019 秒，仅作为执行回执，不用于成本或吞吐率优化结论。

69 个字段的规范类型分布来自本次扫描：

| 类型 | 字段数 |
|---|---:|
| INT / UINT | 11 / 11 |
| LONG / ULONG | 8 / 7 |
| SHORT / USHORT | 7 / 6 |
| SCHAR / UCHAR | 8 / 10 |
| RECORD | 1 |

22 个 INT/UINT 中有 3 个受 const/volatile 限定；因此当前基本类型/限定符子集拒绝共 50 个，
只有其余 19 个进入正式检查器的声明拼写检查。它们均被 `SINGLE_BASIC_DECLARATOR_REQUIRED` 拒绝。
当前正式实现按前置条件顺序提前返回：**50 个类型原因和 19 个声明原因是实际首个拒绝，
不能说正式扫描实际走到了后面的全部布局/别名检查。**
后面的多标签统计来自独立运行的原生发现检查器，对同一批字段逐项检查，而非把首个原因当全部原因。

### 语言必要条件与工程支持范围

必要的语言事实包括合法位域基本类型/宽度、目标确实直接引用该字段并取地址、
以及没有独立的非预期约束违反。完整位宽和值域保持是当前 MR 隔离模型的要求，不能退回任意 `int:1`。
但禁止 union、typedef 拼写、非零初始化、所有指针/数组或非局部对象，均不是 C11 对合法 P0 的普遍禁止，
而是现有闭合证明范围的限制。标准还允许实现定义的其他位域类型，故不能将 LONG/CHAR 等当前拒绝都宣称为语言必然非法。
const/volatile 也不是一律非法位域；本实现没有独立证明改变这些成员后的限定符及观察行为。

`sizeof(record)` 可能观察布局变化，但不因成员成为位域而必然非法；`sizeof(field)` 在目标成为位域后则可能独立违反 6.5.3.4p1。
二者不能混为同一种错误。未分类使用和别名逃逸表示尚未证明闭合，不表示已经发现语言错误。

## 4. 本次唯一扩展：目标依赖范围内的布局独立性

选择这一扩展，是因为布局 veto 覆盖全部 69 个字段，且其精确化可独立验证、复用于后续关系研究；
**不是因为预期单独消除它就能得到正候选**。基准已经显示它与其他阻碍共同存在。
本次没有顺便扩展 typedef 编辑、数组/指针对象、union 或普通成员读写。

新模块 `scoped_layout.py`：

1. 按 P0 物理 token 清点布局标记，并要求每个 sizeof/_Alignof 标记精确对应一个可靠的 AST 操作。
2. 读取操作数实际类型及其子树声明引用；类型图沿 canonical pointer、array、record fields 和函数原型的参数/返回类型传播。
   typedef 经规范类型解析，不用类型名或字段名是否出现在文本中判断关联。
3. 记录类型按 canonical USR 区分；直接或间接到达目标记录，或引用其字段时均拒绝独立性。
   即使指针宽度可能另有证明，也保守保留指向目标类型的依赖。
4. 无法闭合的类型、VLA、宏映射、未对应的关键字、复杂且无完整操作数类型 cursor 的 type-name 都继续拒绝。
   对没有子 cursor 的 builtin type-name 只接受明确的基本类型语法，不把数组界限子表达式的 int 类型当成整个数组操作数。
5. 本次只可消除已证明无关的 sizeof/_Alignof。pragma、属性、offsetof、静态断言等其他标记仍保留 veto，未尝试同时精确化。
6. 只从旧发现层字段的原因集合删除 `LAYOUT_SENSITIVE_CONSTRUCT_IN_FILE`，其他原因完全不变。
   原生扫描器源码未修改，旧接口默认不启用扩展。

37/69 个字段的所有布局操作在当前子集中均可证明独立；其余 32 个含未支持的 pragma，保持拒绝。
该结果只消除了一个不必要的文件级阻碍，不说明这些字段的别名、对象、声明或其他使用已闭合。
实际正式检查仍在更早的类型/声明拼写条件停止，因此安全候选数没有变化。

依据公开 [WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf) 6.5.3.4p1–p3：
sizeof 由操作数类型决定，VLA 有额外求值规则，_Alignof 由操作数类型的对齐要求决定。
结合原来的无逃逸及全使用闭合子集，目标记录不可达的已知操作数类型不会因这次字段声明编辑而改变。
6.5.3.2p1、6.7.2.1p4/p5/p10 仍提供原 MR 的取地址及合法完整宽度依据。
本次成功访问原 WG14 草案；它不是正式付费出版物。

## 5. 见证、独立性与人工验证

保持 `BitfieldConstraintWitness` schema 兼容，新增证明保存在既有 isolation/native_proof 字典中：
目标源哈希及字段/记录身份、全部布局操作的物理锚点和 token 清单、操作数类型图、声明引用、
未闭合原因、证明状态及内容一致性 seal。seal 用于检测数据变更，不是第三方签名或完整性证明本身。

原 MR 仅增加可选 native_scanner 参数和新证明的重放检查，默认选址及诊断合同不变。
生成器仍只分析 P0；新增纯重放器核对源字节、锚点、身份绑定、操作覆盖、类型图和其他影响闭合状态。
它不调用编译器、不解析 P1，不把 AST 前端或一致性 seal 冒充完整 C11 形式化验证器。
保存的 AST/type facts 由受限检查器提供，重放负责内部一致性，不能重新推导任意 C 源码的全部语义。

先通过 14 项新增测试和人工最小 P0，再开始真实扩展扫描。
人工例：目标记录对象 `{0}` 初始化，两处原有 `&object.x` 位于不同语句，其中一处在内层块，
另有无关数组 sizeof、builtin sizeof(int) 和 _Alignof(int)。
旧检查器拒绝，新检查器有 1 个安全字段和 2 个地址点；使用 `signed int x : 32`，没有窄化。
P0 两边 rc=0，P1 两边 rc=1，均精确报告 6:12 和 7:14 的两个目标 error，无额外 error。
人工不是来自真实语料，不能混入 50 种子的适用率。

Oracle 先写入磁盘并记录 SHA256、屏障时间和独立重放结果，再编译 P1，之后核对文件哈希不变。
新增测试在 P0 准入后禁止 subprocess 和所有 P1 AST 解析，仍可构建并重放 Oracle；
身份、位置、类型图或影响闭合证据篡改会被拒绝，即便重算 seal 也不能放过互相矛盾的关系。
另覆盖直接相关布局、typedef/数组/指针/嵌套/函数原型传播、同名不同字段、多地址、宏/pragma/VLA、
非零初始化/非局部/逃逸拒绝、拒绝不生成 P1、UTF-8/CRLF 精确坐标、解析失败及默认 2E 行为。

首轮新增测试发现一个实现问题：`sizeof(int[3])` 的界限 literal cursor 被当作完整表达式操作数。
已增加物理 token 前缀与操作数形状检查，保守拒绝该未支持的 type-name；失败及修复日志均保留。
这是本次检查器开发问题，不是编译器缺陷，也没有用该规则对真实种子生成 P1。

## 6. 客观语义上下文与复杂性边界

`native_contexts.py` 输出 69 个字段、2,410 个地址关系的可复现记录，包括全部相关主文件对象/形参声明、
规范类型和限定符、成员使用数量、全部目标地址、声明与使用函数/作用域/语句单元、真实身份路径、
类型传播路径、字节/行跨度、Native 来源、是否安全闭合及拒绝原因。
没有加入主观难度分、LLM 或 Bandit 特征编码器。
`semantic_contexts.json` 是带完整计数与轻量字段指标的聚合索引；每项使用文件路径、JSON pointer 和 SHA256
指向 `experiment/scans/seed_NNN.json` 中的完整上下文，避免重复保存全部声明与路径。完整细节没有丢弃。

| 原始结构观察，按字段去重 | 字段数 |
|---|---:|
| 声明与目标使用跨语句/声明单元 | 69 |
| 通过同一字段身份关联的跨词法作用域使用 | 66 |
| 同一 canonical 记录/字段类型在多个函数内形成真实引用路径 | 49 |
| 简单局部表达式类 | 0 |
| 优先分类：跨函数共享类型 / 跨作用域 / 跨语句 | 49 / 17 / 3 |
| 上述任一类别的安全原生候选 | **0** |

三个跨越标志非互斥；最后一行优先分类才是互斥分区。词法跨度必须配合同一字段 USR 的引用链，
不是因为两个变量处在不同作用域就算有关系。
跨函数这里是**静态类型依赖**，不是已经证明的跨函数别名或运行时数据流；所有字段的后者均为 NOT_PROVEN。
相关声明的规范类型图最大路径深度分布为 3:9、4:20、5:24、6:6、7:9、8:1。
它统计 pointer/array/record-field 边的已观察简单路径，不是执行传播深度，也不作为深层候选的主观评分。

可追溯例子：`seed_0004_1594631173.c` 的 U0::f1，声明 31:13，USR `c:@U@U0@FI@f1`，规范 INT，
通过原有成员引用连接 `func_29` 的 634:29 与 `func_31` 的 917:22 两个地址操作。
前者基对象引用 g_142，后者引用 l_576；原始声明/类型/成员/地址链均保存在 JSON。
它确有跨函数共享类型关联，但 union、typedef 拼写、对象传播等尚未闭合，**不是安全 MR，也没有证明这两个对象运行时别名相同**。
长代码行、远距离、程序中有多个函数或 AST 层数深均没有被直接作为成功依据。

## 7. 真实结果与诊断边界

扩展后的同一固定 50 项全部完成且仍无安全候选，故实际真实原生 P1 为 0。
没有候选就没有真实 P1 的编译诊断；不能把人工例的结果填入真实种子表。
没有新增增强模板，没有转而执行其他 MR。
没有发现本阶段真实诊断异常候选，也没有确认编译器 bug；未进入真实 P1 分支不意味着已证明编译器没有诊断缺陷。

人工验证继续固定 GCC 15.1.0 / Clang 22.1.0，参数 `-std=c11 -fsyntax-only -w -I <原runtime>`。
保存完整命令、stdout/stderr、返回码、error 结构、全部目标对应关系、源码 diff、SHA 和重放结果。
仅 error/fatal 可通过，未加 Werror；unknown、缺少目标或精确位置差异分别保留为待复核，
没有 ±1、模糊相似度或 unknown 放行。崩溃、超时、执行失败与普通诊断异常分开。
C11 的诊断义务与项目严格 error 合同不同，不声称标准规定唯一 caret。
诊断观察器源码没有修改，也没有依据 P1 诊断修改 Oracle。
